Existing client and flow:
- backend/app/adapters/nessie.py: NessieClient.request()/query(), API_BASE,
  REMOTE_ID and QUERIES. Reuse this client; no second HTTP client was added.
- backend/app/services/workspace.py: context(), refresh(), collection(), movements(),
  token(), account_codes(), require_nessie().
- refresh GET /customers/{remote_customer}/accounts requires row.customer_id to
  equal the selected remote customer, and validates account IDs/type/balance/rewards.
- Each account is fetched through /accounts/{remote_account}/{purchases|transfers|
  deposits|withdrawals}; collection rejects duplicate/malformed remote IDs.
  Both _id and id are accepted, but conflicting simultaneous values reject.
- scope = SHA256(NESSIE_API_KEY UTF-8).hexdigest() (64 lowercase hex).
  customer_code = persisted customer_<uuid4.hex> alias scoped to root user + key hash.
  owner = DEMO_USER_ID + ':nessie:' + scope + ':' + customer_code.
  account_token = 'acct_' + SHA256(owner + ':' + remote_account)[:32].
  transaction_id = 'txn_' + SHA256(owner + ':' + plural_collection_kind + ':' +
      remote_account + ':' + remote_transaction_id)[:32]. All hashes are hex strings.
- The same transfer can yield two distinct account legs. Payer leg is debit,
  payee leg credit. Both/neither matching when parties exist rejects the collection;
  absent payer AND payee produces unknown direction, not an invented party.
- Save replaces a successful per-owner/account/kind collection, with owner-keyed
  constraints; repeated retrieval does not append duplicates. Failed collections
  retain the safe cache, while live product actions fail rather than use fixtures.
  Snapshot exposes at most the current 100-record analysis window.
- Transaction service, reviews, analyses and memory operations derive the same owner
  through workspace.owner(); customer codes cannot resolve outside root/key scope.
- KEY ROTATION CHANGES owner, account and transaction tokens and memory/review identity.
  Returning to the old key reuses old aliases only while the original DB persists.
  A fresh DB regenerates random customer aliases even with the same key/customer.
  Do not change this algorithm or migrate owners without coordinated approved design.
