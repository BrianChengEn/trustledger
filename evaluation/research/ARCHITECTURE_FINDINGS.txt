# TrustLedger 架構研究

這次的問題是：以現有、可獨立標註的交易資料，哪一種架構最能找出可疑交易，同時少漏報、少誤報，而且解釋得清楚、守得住隱私。

結論先說。

**目前有地面真相支持的最佳架構，是伺服器本機的非線性評分模型。** 輸入是精確金額、資料源能提供的類別，以及客戶編號可信時的歷史。模型用 HistGradientBoosting。人工審核預算決定要看前多少筆，而不是每筆都呼叫一個大型語言模型。

**Jev 和 Gemini 的偵測貢獻沒有被測到。** 現有八欄 SafePayload 的資訊上限，在 BankSim 上低於本機的精確金額。因此不能說再加一個外部模型就會更準。Gemini 原本就被設計成解釋層，不是第二個偵測器。

這不是上線級的金融模型。兩個資料集都是模擬器。BankSim 沒有幣別。本機的 Sparkov 檔不是官方 Kaggle 原檔。

## A. Gemini 原始設計稽核

Gemini 這個詞第一次出現在 commit `aae05b4`（2026-10-17，benson5112，`feat(backend): implement F1-F8 provider interfaces and reliability`）。更早的 commit 沒有這條字串。

`docs/prompts/backend-scope.md` 把系統寫成：Nessie 提供交易，Jev 做風險評估，Gemini 是未來的解釋層。同一份文件要求延後真正的 Gemini client，而且不准用 Gemini 取代 Backboard。

`docs/prompts/backend-features/F5-fraud-analysis-orchestration.md` 寫明詐欺分析不要納入 Gemini，解釋留給 F7。`F7-explanation-interface-mock.md` 的任務是做一個可替換的內部介面，不接真實 SDK、金鑰或網路。

`backend/docs/explanation-proposal.md` 的狀態是：內部 mock 已做，Gemini 的 HTTP 與前端整合仍是提案。請求只允許既有的八欄特徵，加上已經決定好的 `alert_type`、`severity`、`needs_human`。結果的 `source` 只能是 `mock` 或 `fallback`，測試會拒絕 `source=gemini`。它不能改風險判斷，也不能下金融動作。

所以六個問題的答案是：

1. Gemini 有被規劃，但是未來的解釋層，不是原始偵測器。
2. 它的角色是把已經做出的規則判斷，說成一段受控的說明。
3. 它沒有被設計成和 Jev 互相修正。順序是規則先決定，Jev 可選擇性標註來源，解釋層在決定之後。F5 禁止把 Gemini 放進詐欺分析。
4. 目前沒有 Gemini SDK、網址、模型名稱或傳輸。`ExplanationService` 只用審過的模板。`backend/README.md` 寫 Gemini 尚未實作。
5. 介面還在，而且刻意不接進路由。以後可以加解釋，不必把警示決定權交出去。
6. 現在的偵測限制見下一節。

## B. 現在的 TrustLedger 偵測架構

最新 `origin/main` 是 `faf8c41`。`backend/app/core/rules.py` 相對先前的 `2f97f1a` 沒有差異。HTTP 規則是：

- 同一商家、同一金額、24 小時內的借記：`duplicate`
- 否則借記金額 `>= 250`：`amount_anomaly`
- 否則同一商家的訂閱漲幅 `> 20%`：`subscription_change`

`backend/app/core/fraud.py` 的 `evaluate_fraud` 在 Jev 成功時只更新 `provider_mode` 和 `model_version`。註解寫明不取代規則的嚴重度、信心、證據或是否需要人工。失敗則標成 `degraded`，規則結果保留。

送給外部模型的 SafePayload 只有八欄：類別、金額區間、幣別、時段、24 小時同類別同金額次數、是否訂閱、訂閱變化區間、先前確認。精確金額、商家文字、帳號和姓名都不出去。

交易物件本身有精確金額、時間、商家顯示名、類別、帳號 token、借貸方向和訂閱旗標。這些可以留在伺服器上做本機評分。

## C. 研究發現

兩個模擬器的詐欺標籤都和金額有關，但方式不同。

BankSim 全檔 594,643 列、7,200 筆詐欺。金額高的交易比較容易是詐欺，所以一條 250 門檻在它上面的 precision 還能看。類別基礎率單獨並不夠：原生類別的訓練期詐欺率，在測試集的 average precision 只有 0.464，低於金額排序的 0.704。

Sparkov 這份匯出有 1,048,575 列、6,006 筆詐欺。`unix_time` 從 2012-01-01 排到 2013-03-10，和官方 Sparkov 常被描述的 2019–2020 不一致。卡號大量是科學記號，所以這次不用客戶歷史。在這份檔案裡，金額 `>= 250` 會把大量正常消費一起抓進來。類別基礎率更弱，測試集 average precision 只有 0.015。有用的是金額和類別的交互作用，例如同一類別裡異常高的金額。

目前系統的主要瓶頸不是「少了一個 LLM」。瓶頸是決策只用一條固定門檻和很窄的重複扣款條件，而且外部模型看得到的欄位比伺服器少。

文件裡的「30 天同類別中位數 3 倍」在產品類別映射後的 BankSim 上比 250 門檻差。映射把 120 筆三天窗詐欺裡的大多數收成 `other`，中位數被混在一起。這條規則不該在沒有更細類別時直接換上。

客戶自己的金額 z-score 單獨使用時很弱。BankSim 的詐欺常常就是一筆偏高的金額，不是相對這個客戶的極端值。

## D. 比較過的架構

產品可實作的一組，只用伺服器看得到、而且不依賴 BankSim 原生類別名稱的特徵：

| 代號 | 假設 |
| --- | --- |
| prod_rules | 現在的商家重複或金額 >= 250 |
| doc_rules_mapped | 文件規則：映射後類別的 24 小時重複，或大於 30 天中位數 3 倍且大於 100 |
| amount_score | 金額本身就是風險排序 |
| customer_z | 相對客戶歷史的極端程度 |
| safe_payload_lr | 只用金額區間、映射類別和重複次數。這是外部模型的資訊上限，不是 Jev 的真實輸出 |
| explainable_lr | 線性模型，使用精確金額和客戶歷史，沒有類別身份 |
| history_hgb | 同一組歷史特徵的非線性模型 |
| mapped_lr / mapped_hgb | 再加上產品的七個類別 |

另外一組只用來診斷資料，不拿來當產品建議：原生類別的邏輯迴歸、原生類別的梯度提升、類別基礎率。Sparkov 上再測金額、250 門檻、金額加類別的線性與非線性模型。

Jev 先跑、Gemini 後跑、每筆都呼叫 LLM，這三種都沒有列成必測架構。現有程式已經規定 Jev 不能改決定。在呼叫付費 API 之前，先看外部模型就算完美，也只能看到八欄之後還剩多少訊號。

## E. 實驗方法

BankSim 依 `step` 切。0–119 訓練，120–149 驗證，150–179 測試。測試有 111,306 列、1,200 筆詐欺。特徵只用該筆之前的歷史。24 小時比較和 `core/rules.py` 一樣，日內順序是檔案順序。類別統計和 one-hot 欄位只從訓練期建立。門檻和模型選擇只用驗證集的 average precision。差距在 0.01 以內就選較簡單的模型。測試集沒有用來選模型或調門檻。

Sparkov 依 `unix_time` 排序。最早 70% 訓練，接著 15% 驗證，最後 15% 測試。測試是 2012-12-24 到 2013-03-10，157,287 列、953 筆詐欺。沒有使用卡號、姓名、地址或客戶歷史。

指標是 average precision、precision、recall、F1、FPR，以及相同審核數量下的比較。沒有把 accuracy 當選擇標準。

## H. 怎麼讀這些差異

BankSim 上，金額排序和現行規則在同一個操作點幾乎一樣。規則的本質就是 250 門檻，重複扣款幾乎沒有改變結果。所以只在 BankSim 上調 250，不會得到新系統。

Sparkov 上，同一條 250 門檻的 precision 掉到 0.155。金額和類別一起交給非線性模型之後，average precision 從 0.199 升到 0.716。線性模型沒有學到這個交互作用，所以不建議用邏輯迴歸當偵測器。

客戶歷史在 BankSim 有真實客戶編號時有幫助：沒有類別的 `history_hgb` 測試 AP 是 0.801，金額單獨是 0.704。Sparkov 這份檔案無法誠實地重做這個實驗。

八欄上限的邏輯迴歸測試 AP 是 0.524，低於精確金額的 0.704。外部模型若只能看到金額區間，排序能力會先被欄位砍掉。這不是 Jev 或 Gemini 的實測準確率。它們的真實輸出沒有用在這次評分裡。

## I. 失敗長什麼樣子

BankSim 上，`mapped_hgb` 在 919 筆預算裡漏掉 414 筆。這些漏報金額的 10、50、90 百分位是 19.0、120.8、259.6。中間那批是低於舊門檻、但模型也沒有把它們排進前 919 的詐欺。誤報金額的中位數是 242。

和現行規則比，召回提升較明顯的類別包括 wellness、leisure、fashion、home、hyper。`es_barsandrestaurants` 的召回仍只有 0.308，`es_hyper` 是 0.312。交通類在這個測試窗沒有詐欺標籤，規則卻對它發了 13 次警示。

文件規則的失敗更直接：映射後的中位數規則在測試集只有 recall 0.328、precision 0.349，兩項都低於 250 門檻。

Sparkov 的失敗是固定門檻不看類別。正常的高額購物被大量送進審核。類別名稱單獨也不行，因為同一個類別裡同時有正常消費和詐欺，差別在金額相對該類別的位置。

## J. 建議的架構

### 現在證據支持的做法

1. 每筆交易在伺服器計算本機分數。特徵是精確金額、來源提供的類別、客戶歷史（筆數、距上次天數、是否新商家、相對自己的過去金額），以及可信的客戶編號。
2. 分數用非線性模型。這次驗證通過的是 HistGradientBoosting。類別有意義時把它放進模型。BankSim 上它只比沒有類別的歷史模型多抓約 10 筆，所以類別映射不可靠時，可以退回 `history_hgb`。
3. 用審核預算決定門檻。要比較時，鎖住警示數量再看 recall 和 precision。
4. 規則可以留作可解釋的下限或理由碼，例如「金額高於這個客戶在該類別的平常水準」「新商家」。理由碼和分數一起顯示。理由碼不要再做成另一條會蓋過模型的硬門檻，除非另外做過校準。
5. 精確金額和商家留在伺服器。不要為了提高準確率把它們加進外部 payload。
6. 模型必須用實際上線資料的金額尺度重新訓練或校準。BankSim 的 250 不能直接搬到另一個金額分布。Sparkov 已經證明這件事。

在 BankSim 相同的 919 筆預算下，這個做法的 recall 是 0.655，現行規則是 0.584；precision 是 0.855，現行規則是 0.763。在 Sparkov 的 F1 操作點，金額加類別的梯升模型 F1 是 0.667，250 門檻是 0.257。

### Jev

維持現在的契約：不能取代規則的警示決定。這次沒有證據顯示它能提高偵測。若 payload 仍是八欄，一個完美的外部分類器在 BankSim 上的排序上限仍低於本機金額。在擴大並核准欄位之前，不值得為了偵測準確率去花 API 費用。

### Gemini

維持解釋層的定位。它應該讀本機模型已經產生的理由碼和八欄特徵，產出受控說明。它不應改 `needs_human`、嚴重度或警示類型。這條路線沒有用真實 Gemini 輸出測過，所以它是有理由的下一步，不是已驗證的準確率來源。

### 有希望但尚未實測

- 用理由碼約束 Gemini，並由人評估說明是否忠於分數。
- 客戶編號可信的 Sparkov 原檔，重做歷史特徵。現在這份匯出不能做。
- 不確定分數帶再交給人工或外部模型。剩餘漏報的金額中位數約 121，外部模型又看不到精確金額，所以不能假設 LLM 補得上。這是假設，不是實驗結果。

### 這次拒絕的做法

- 每筆交易都呼叫 Jev 或 Gemini。沒有準確率證據，而且八欄上限已經較低。
- 用邏輯迴歸當主偵測器。兩個資料集上都輸給梯升，Sparkov 上甚至沒有贏過金額排序。
- 只用客戶 z-score。BankSim 測試 AP 0.220。
- 直接換上文件的 3 倍中位數規則。映射後的 BankSim 測試 AP 0.122。
- 只靠類別基礎率。Sparkov 上幾乎沒有區別力。
- 把模擬器訓練好的權重直接放進 demo。金額尺度不同。

## K. 還沒有回答的問題

- 真實銀行或 Nessie 合成帳戶上，金額和類別的分離是否還在。兩個資料集都是模擬器。
- 官方 Sparkov 原檔、可用的客戶編號，歷史特徵能否再提高一截。
- 本機模型的理由碼，人是否覺得足以解釋警示。
- 若將來核准更多欄位給外部模型，Jev 能否在本機分數之上提供增量。現在沒有這個實驗。
- 訂閱漲價仍然沒有外部標籤。

## 實作順序

黑客松期間不要把警示決定權從規則改到模型。那會改到 `core/rules.py` 的產品行為，而且權重還沒在 demo 的金額尺度上校準。

下一步可以做的是一個隔離的本機評分器：算分數和理由碼，不覆蓋現有警示。權重用部署資料自己的訓練切分，不把這次的 BankSim 模型檔放進產品。

黑客松之後再考慮：決定權轉移、人工評估解釋、官方資料重跑，以及任何付費模型實驗。付費實驗要另外授權。這次沒有呼叫 Jev、Gemini 或 Backboard。

研究腳本和報告由 Grok 協助撰寫。產品規則、API 契約和隱私邊界沒有修改。
